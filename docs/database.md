# DB設計の補足

## 参照した設計書

- `26_テーブル設計書.xlsx`（2026/11/17改訂）：テーブル一覧、各テーブル定義、設計補足23～35の企業分離・初期発行・移行方針。
- `22_ユースケース図.xlsx`：UC07の情報破棄、UC21の回答保存、UC24のメール送信等の業務フロー。

今回のSQL修正ではExcelファイルを変更していません。初期化SQLには26テーブル・215列を定義し、物理名、列順、データ型、桁数、初期値、PK、FK、NNを反映しています。日本語の論理名と備考は`COMMENT ON`でDB内にも保持します。

## SQLで保証する範囲

- IDは`BIGINT GENERATED ALWAYS AS IDENTITY`。日時は`TIMESTAMPTZ`。
- 初期値が空欄の列には既定値を追加しません。保存日時・版番号等はアプリが明示します。
- 備考にある一意性を`UNIQUE`で表現します。応募は回答ごとに1件、メールは回答・応募版ごとに1件、下書きはアンケートごとに1件です。
- `companies`を追加し、既存25テーブルすべてに`company_id BIGINT NOT NULL`と企業へのFK、`UNIQUE (company_id, id)`を設定します。既存の`id`単独PKは維持します。
- 従来の41本のFKを`(company_id, 参照ID)`から親の`(company_id, id)`への複合FKに変更します。企業への25本を合わせ、FKは66本です。任意参照は`MATCH SIMPLE`で従来どおりNULLを許容します。
- 募集コードは`(company_id, code)`、雛形版は`(company_id, hire_type, version_no)`で一意です。企業コード、担当者メール、受付番号、公開コード、応募リンク・受付確認キー、各送信識別子の全体一意性は維持します。
- 状態・区分のコード、年度1000～9999、正の版番号・表示順、非負の世代・試行回数、0～4の評価段階、0～100の得点、開始日時より後の終了日時等を`CHECK`で検証します。
- 記述回答と選択回答はどちらか一方だけを保存します。案内メールと受付メールの参照先を区別し、受付メールにアンケート別メール版を指定できないようにします。
- 加点項目の最大配点、確認済み抽出項目の確認者、得点確定時の合計点、送信成功時の文面・送信日時等の、同じ行で判定できる必須条件を検証します。
- 判断登録時は確認済みフラグがTRUEで、理由が空文字でないことを検証します。設問選択肢の空文字も拒否します。
- 外部キーには`ON DELETE NO ACTION`と`ON UPDATE NO ACTION`を指定します。参照が残っていれば削除・主キー変更を拒否します。
- 各複合FKの参照元に`(company_id, 参照ID)`の索引を追加します。企業単独の検索は`UNIQUE (company_id, id)`の索引も利用できます。旧SQLの単独FK用索引は企業を先頭にする索引に置き換えます。
- 25テーブルの`company_id`変更をトリガーで拒否します。既存レコードを別企業へ移す通常操作は提供しません。
- 26テーブルでRLSを有効化・強制します。`salt_app`の企業データ25テーブルに対する閲覧・書込みは、企業Contextとの一致と企業の有効状態を必要とします。`companies`は自社行の参照だけを許可し、利用停止状態の確認にも使います。

DDL全体を1トランザクションで実行し、途中で失敗したときに一部のテーブルだけを残さないようにしています。`CREATE TABLE IF NOT EXISTS`は使わず、既存スキーマとの不一致を隠しません。

`db/init/001_create_tables.sql`と移行SQLは、共通の`db/init/shared/tenant_security.sql`を`psql`の`\ir`で読み込みます。共通ファイルは単独実行せず、ディレクトリ構成を保ってコピーしてください。Dockerの初期化処理はサブディレクトリを再帰実行しないため、二重適用にはなりません。

## アプリ用の接続と企業Context

`POSTGRES_USER`は管理用です。通常のアプリでは、初期化SQLが作る`NOLOGIN`の権限ロール`salt_app`を継承する専用ログインを使用します。管理用の`psql`で、環境ごとに次のように作成します。パスワードをSQLファイルやGitへ書き込まず、`\password`で対話設定してください。

```sql
CREATE ROLE salt_web LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE
    NOREPLICATION NOBYPASSRLS IN ROLE salt_app;
\password salt_web
```

`salt_app`には企業データ25テーブルのSELECT・INSERT・UPDATE・DELETEと必要な採番権限だけを付与します。企業の新規登録・停止、DDL、TRUNCATE、運営権限は付与しません。テーブル所有者・スーパーユーザー・BYPASSRLSを持つ接続を、アプリの接続プールに使用しないでください。

認証済み担当者、検証済み公開URL、保存済みジョブからサーバーが企業を確定し、毎回のトランザクション内で設定します。次はドライバーのバインド変数`$1`に、信頼済み企業IDを文字列として渡す例です。

```sql
BEGIN;
SELECT set_config('app.company_id', $1, true);
-- company_idで絞り込み、役割・担当募集・対象IDもアプリで照合して操作する。
SELECT id, code, job_title FROM openings WHERE company_id = app.current_company_id();
COMMIT;
```

`true`により設定はトランザクション終了時に解除されます。企業ID未設定・空文字の場合は企業データを取得できず、登録も拒否します。セッション単位の`SET app.company_id`や`set_config(..., false)`は使用しません。企業IDを設定できるDB資格情報は信頼済みサーバーだけに保持し、契約企業やブラウザーに配布しません。RLSは企業IDそのものの認証を行う仕組みではありません。

ログイン前のメール照合や公開トークンからの企業特定は、企業Contextを設定する前に必要です。アプリ実装時には、必要な情報だけを返す専用認証・トークン解決処理を別途用意します。通常の`salt_app`に全企業のstaff・応募情報を読む権限を追加したり、通常の画面処理を管理接続へ切り替えたりして解決しないでください。このリポジトリには認証・公開URL処理そのものはまだありません。

企業停止時はRLSでも通常の業務データ操作を拒否しますが、外部のメール・AI・ストレージ操作、実行中ジョブの取消、役割・担当募集の判定はアプリの責務です。開始前と結果確定・送信直前に再確認し、停止との競合も制御してください。必要な破棄・保守は、アプリから分離した運営用接続で対象企業を明示して継続します。

## 企業と初期リーダーの登録

`db/scripts/create_company_admin.sql`を運営用接続から実行します。次の5つのpsql変数を必要とします。

| 変数 | 内容 |
| --- | --- |
| `company_code` | 全体で一意の企業コード |
| `company_name` | 企業名 |
| `leader_name` | 最初のリーダーの氏名 |
| `leader_email` | アプリと同じ方式で正規化した、全体で一意のメール |
| `password_hash` | アプリと同じ方式で生成したパスワードハッシュ |

企業と`role='admin'`・`is_active=TRUE`の担当者を同一トランザクションで作ります。企業コードまたはメールが重複すると全体が失敗し、既存アカウントは上書きしません。SQLは平文パスワードを受け取ってハッシュ化する機能を持ちません。認証実装と方式を統一したハッシュを、運営用の呼出スクリプトから安全に渡してください。平文パスワードや実際のハッシュを共有SQL・Git・ログに保存しないでください。

企業内の`admin`は運営管理者ではありません。2人目以降の担当者追加では、認証済みリーダーの企業IDをサーバーが強制設定し、クライアントの企業指定を受け付けません。

## 旧25テーブルからの移行

`db/migrations/001_add_companies.sql`は、このリポジトリの旧25テーブル・185列のDBを、確認済みの1企業に割り当てる移行です。既存ID・パスワードハッシュ・業務データ・採番は保持します。旧データが複数企業に属する場合は使用せず、親子関係に沿った企業割当表を作成して移行SQLを調整してください。

1. アプリ・ワーカーを停止し、バックアップと復元手順を確認します。
2. 全既存データの所属企業を確認し、下記の企業コードと企業名を実際の値へ置き換えます。
3. 管理接続で実行します。`confirm_single_company=yes`は「全既存データがこの1企業に属する」と確認した場合だけ指定します。

```sh
docker compose cp db db:/tmp
docker compose exec db sh -c 'psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v company_code=ACME -v company_name="株式会社サンプル" -v confirm_single_company=yes -f /tmp/db/migrations/001_add_companies.sql'
```

全対象テーブルをロックし、企業作成、NULL許可での企業ID追加・割当て、NOT NULL・複合FK・UNIQUE・索引・RLSの設定を1トランザクションで行います。想定するテーブル数・列数・FK数の不一致、未確認、制約違反、再実行はエラーにし、部分適用しません。独自に変更した旧スキーマは、事前にこのリポジトリの旧SQLとの差分を確認してください。ロックを10秒以内に取得できない場合も終了します。

移行後は既存データの企業所属、企業リーダーの有無、アプリの企業Context設定を確認してから再開します。既存担当者の権限を自動でadminへ変更しません。`storage_key`も書き換えないため、既存ファイルの企業別プレフィックスへの移動とキー更新は、実ファイルを確認した別の移行処理が必要です。

## 実装で補足した点

- チームで確認したPostgreSQL 18.7を使用します。
- PDFの10MB上限は、確認した10,485,760バイト（10MiB）として`size_bytes`に適用します。実ファイルのバイト数・PDF形式・読取可否はアプリでも検証します。
- 各種`version_no`は1以上、抽出世代は0以上として統一しました。
- 同一設定版への同じ募集の二重登録は`UNIQUE (survey_version_id, opening_id)`で拒否します。ただし異なる募集IDで採用区分が同じ場合の重複はアプリで検証します。
- 評価明細では段階と得点を両方NULLまたは両方非NULLにし、必須条件の判定と加点の同時登録を拒否します。基準項目との照合や得点計算は以下のアプリ側検証に含めます。
- 氏名・メールなどのNNはNULLのみを拒否します。必須入力の空白・形式・文字数の検証もアプリで行ってください。`staff.email`は保存値に対する一意制約です。正規化の方法を認証実装で統一し、登録時とログイン時に同じ処理を適用してください。

## アプリ側で必要な検証

初期化SQLはテーブル・制約・企業分離を作成するものです。次の複数行・複数テーブルにまたがる業務条件は、現時点ではDBトリガーで実装していません。対応する保存処理のトランザクション内で検証してください。

| 対象 | 検証・処理する条件 |
| --- | --- |
| 企業・権限 | 認証済み企業IDの設定、staffの有効状態、role、担当募集、公開トークンの用途を検証。全ての一覧・詳細・検索・集計・書込み・ファイル取得を自社の許可範囲に限定すること。 |
| 評価基準 | 基準版ごとの加点項目の最大配点合計が100点であること。版番号の採番を同時保存でも重複させないこと。 |
| アンケート対象募集 | 同じ設定版・採用区分の募集が1件までであること。採用区分は`openings`から取得。 |
| 設問・回答 | 選択肢は選択式設問のみ。回答と設問が同じ設定版であること。選択肢が同じ設問に属し、設問の回答形式と値が一致すること。必須回答がそろうこと。 |
| 公開・期限・下書き | 必要な設定・メール・設問を検証してから公開。最新の確定設定版の受付期間を回答・応募・編集時に照合。下書きは公開・受付・送信に使用しないこと。JSON内の募集ID・元テンプレート版IDも自社所属を確認すること。 |
| 応募 | 選考希望のある回答だけを応募に結び付けること。応募時の同意、判断登録後の編集禁止、最新版・書類・解析予約の一括保存。 |
| メール | 希望なしでは案内行を作らないこと。送信用メール版が回答元と同じアンケート・採用区分であること。対象区分・コピー元テンプレートの整合、本文の差し込み変数を検証。宛先と期限を照合し、送信成功済みを再送しないこと。 |
| 書類・抽出 | 新卒の履歴書、中途の履歴書と職務経歴書を必須とすること。抽出根拠の書類が同じ応募版に属すること。保存先は`companies/{company_id}/applications/{application_id}/...`で分離し、取得・削除時にも権限照合すること。確認済み抽出行は更新せず履歴を追加。 |
| 解析 | 最終送信成功の2時間後に最新応募版だけを解析。修正時は確認済み世代で即時再計算。旧版の予約・結果を最新として使わないこと。 |
| 評価 | 基準版が対象応募と同じ募集で、明細が同じ基準版の項目を参照すること。根拠書類は同じ応募版に限定。項目区分に応じた段階・判定、最大配点×段階÷4、全明細の合計・未評価を検証。 |
| 最終判断 | 評価が同じ応募の最新かつ有効な評価であること。応募単位のロックで編集・再計算・判断の競合を防ぐこと。 |
| ログ | `target_type`と`target_id`は複数テーブルへの論理参照なので、アプリで自社所属を検証。個人関連ログには`response_id`を付け、パスワードや書類本文を記録しないこと。企業に属さない運営全体ログは別管理とすること。 |

企業一致は複合FKで保証していますが、同一企業内の募集・応募版・設問版まで一致するとは限りません。通常の`CHECK`には他の行・テーブルを直接参照する検証を持たせられないため、上記の業務条件は保存処理で照合し、DBでの保証が必要になったものから追加の制約・トリガーを検討してください。

## 情報破棄と設計上の未確定事項

設計書は、見送り時に`applications.purge_status`を`deleting`へ変更し、アクセス・書込を停止した後にファイルと関連データを削除する方針です。自動連鎖削除を付けるとファイル削除・再試行の管理を飛ばせるため、ここでは明示的な削除を前提にしています。

全応募版のファイルを削除した後、判断 → 評価明細 → 評価 → 抽出 → 解析 → 書類 → メール → 応募版 → 応募 → 回答明細 → 関連ログ → 回答の順で削除します。DB内の削除はトランザクションで行い、失敗した場合は破棄中を維持して再試行してください。DDLだけでは破棄処理は動作しません。

設計書で未確定とされている、次選考・保留・未応募・選考希望なしの保管終了条件、バックアップや外部ストレージ複製の削除方法は、運用実装前にチームで決める必要があります。
